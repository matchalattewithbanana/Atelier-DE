# Recovery locker input boundary (experimental)

The internal entry state machine is compiled and unit-tested independently of the black-only Wayland client. The entry state is now owned by the private keyboard protocol adapter, but the black-only client cannot enable readiness. There is no unlock request or mapped graphical password prompt.

The eventual locker must derive entry readiness from its exact confirmed lock, successfully mapped surface and uninterrupted keyboard focus. Focus loss, root loss or protocol failure must invalidate pending attempts and clear unsubmitted input. A canceled attempt remains the only active attempt until its worker resolves. Polling never blocks the Wayland event loop. A positive result is consumable once only, with readiness still valid and before the monotonic 30-second deadline; it must be handled after processing pending protocol events and before any unlock request. The result is not itself an unlock capability.

The password uses one bounded 4096-byte allocation, no cloning or debug rendering, UTF-8 character insertion and byte erasure on backspace, cancellation and drop. Submission moves ownership into the authentication thread, which erases its buffer before reporting a result. The renderer is offered only a generic has-input indicator. Control characters are intentionally rejected; compose, keyboard-layout handling and input-method integration are not yet implemented. This is best-effort memory hygiene, not a guarantee against paging, registers, compromised process memory or PAM's copies.

A failed, canceled, disconnected or overdue attempt cannot verify; retries use 1/2/4/8-second bounded cooldowns. This is not a persistent rate limiter and does not replace administrator-configured PAM throttling. The worker implementation must impose its own process deadline; if it never returns, entry remains busy rather than starting concurrent authentication. No real PAM operation is invoked by these tests.

Tests cover bounded Unicode entry, wiping removed bytes, entry readiness, focus-loss and cancel invalidation, single-attempt enforcement, consumed success, late results, worker panic and retry delays. The actual trusted launcher, keyboard mapping, rendering, protocol integration, hardware validation and same-UID isolation remain outstanding. Native locking stays disabled.

## XKB keyboard foundation

The private keyboard module copies a bounded (1 MiB maximum) XKB v1 keymap from its supplied file descriptor, requires a single trailing NUL and valid UTF-8, and compiles without default include paths. It uses compositor-provided modifier masks and checked evdev-to-XKB keycode conversion. The caller must reject unsupported Wayland keymap formats and establish the exact focused lock surface and visible, confirmed prompt. Keymap replacement, focus loss, keyboard removal or invalid topology revoke entry readiness and invalidate pending authentication. Held keys on enter and duplicate presses cannot produce password text. Return requests submission, Backspace edits, and Escape clears or cancels; control/Alt/Super shortcuts are ignored. No compose, IME or repeat handling is provided yet. The module never requests an unlock. Private protocol dispatch is now implemented; prompt presentation and trusted authentication integration remain outstanding.

## Private seat binding and prompt rendering

The black-only client optionally binds exactly one advertised wl_seat at version 3. It accepts keyboard events only from the current keyboard object, validates XKB v1 keymaps and key states, and recognizes focus only on its exact configured root. Capability removal releases the keyboard and revokes its decoder and entry; removed or duplicate seat globals fail closed. A missing seat still permits the original black-only probe. Protocol errors clear input readiness before ending the client. The client never enables prompt readiness and never submits an authentication request. A compositor wire test uses a private recovery endpoint, maps the actual client, confirms the protected frame, forwards key presses, and checks that the desktop remains protected through disconnect.

A separate deterministic renderer builds an opaque XRGB8888 status card into a fresh sealed SHM file, sharing the existing bounded backing-file allocator. It uses embedded bitmap glyphs and fixed strings, with five generic states: ready, entered, checking, retry and unavailable. No password text, exact password length, user-supplied labels, or desktop contents can reach the renderer. It rejects dimensions below 192×144 or allocations above 64 MiB. This renderer has unit coverage but is not yet attached to the Wayland surface. A future interactive client must first present a prompt, enforce exact lock and focus readiness, bound outstanding frame buffers, integrate the trusted authentication worker and process pending protocol events before accepting verification. The original black-only path remains non-interactive and does not unlock.
